# Верстальщик рассылок tsss.site

Задача: взять письма из Google Docs и собрать **черновики** рассылок в GetCourse на tsss.site.
Текст не пишем и не редактируем — переносим ровно то, что в документе.

Это «брат» скилла `gc-mailing` (Life Practic). Техника работы с GetCourse одна и та же, поэтому:
- данные аккаунта tsss — в `config.md` этой папки (читать первым; поля `<…>` не угадывать — спросить);
- эталоны названий, сегментов, UTM и картинок tsss — в `../tsss-mailing-check/patterns.md`;
- рецепты интерфейса GC (копирование, конструктор писем, боты, картинки, теги, пакетный режим) — в `../gc-mailing/config.md`, раздел «Заметки по интерфейсу GC». Всё, что там про Life Practic (подвал, образцы, боты, теги `action-…`), к tsss НЕ относится;
- скрипты — из `../gc-mailing/`: `gdoc_items.py`, `items2emails.py` (разбор документа), `md2gc.py` (HTML почты), `bot2gc.py` (HTML ботов). Запускать `python3 -I ../gc-mailing/<скрипт>`.

## Жёсткие запреты

- НЕ отправлять, НЕ нажимать «Готово к отправке», «Отправить», «Тестовое письмо». Финал — сохранённый черновик.
- НЕ удалять ничего (рассылки, сегменты, файлы, пользователей).
- Работать только в разделе «Рассылки» (и в файловом хранилище для картинок). Не открывать базу пользователей, профили, настройки аккаунта.
- НЕ менять рассылки со статусом «Завершена» или «Готовится к отправке». Черновик с таким же названием уже есть — обновить его, а не плодить дубль (при сомнении спросить).
- НЕ вводить пароль: пользователь сам залогинен в tsss.site в Chrome. Открылась страница входа — остановиться и попросить войти.
- НЕ переписывать, не «улучшать», не сокращать текст. Опечатки — списком в отчёт.
- Латинские буквы в словах («бeсплaтный», «бoнусные») — намеренный антиспам tsss: переносить как в документе, не «исправлять».
- Буфер обмена (Cmd+V) не использовать — портит кириллицу. Ввод только через JS или `type`.
- Чего-то не хватает или неясно — остановиться и спросить.

## Вход от пользователя

**ТЗ** (когда, кому, кого исключить, каналы, картинка) + **ссылка на Google Docs** с текстом.
Какие письма переносить — называет пользователь. Не назвал — показать список писем из документа и спросить.

## Шаг 1. Разбор

1. ТЗ разложить в таблицу: дата и время, каналы (по умолчанию EMAIL + TG + MAX + VK), сегмент «отправляем / исключаем», картинка.
2. Документ: HTML-выгрузка (`download_file_content`, `exportMimeType: text/html`) → `gdoc_items.py` → `items2emails.py`. `read_file_content` обрезает длинные документы (~5 тыс. знаков) — для сборки не годится.
3. Из каждого письма: тема, прехедер, текст, кнопки (подпись + ссылка), текст для ботов (если отдельный), указания из комментариев.
   - Ссылки Google вида `google.com/url?q=…` — извлечь настоящий адрес.
   - UTM ставит автор: переносить как есть. Сверить с эталоном (`source=gk`, `medium` по каналу, `campaign`, `group=crm`) и расхождения — в отчёт, не править. Главная ловушка: в боте ссылка с `medium=email`.
   - `{first_name}` — как есть.

**Показать пользователю таблицу разбора** (письмо → канал → название → тема → прехедер → кнопки/ссылки → время → чего не хватает) и дождаться «да».

## Шаг 2. Создание черновиков

1. Образец канала из `config.md` → **«Копировать»** (сохраняются отправитель, бот, категория «Общие рассылки», настройки chatium). С нуля не создавать.
2. Название по эталону: `[EMAIL] ПРОДУКТ | событие [дд.мм.гг] в ЧЧ`, у TG/MAX/VK тот же хвост.
3. Почта: тема, прехедер, **ОБЯЗАТЕЛЬНО в каждое письмо** — в «HEAD письма» (`Mailing[headHtml]`) дописать `<vk-snippet-end/>` (в образцах поле пустое; без этого черновик не готов), текст и кнопки — по рецепту конструктора из `../gc-mailing/config.md` (или HTML, если образец tsss свёрстан HTML — см. `config.md`). Картинка — по ТЗ (эталоны «Логотип школы» / «С приветственного» — в `patterns.md`).
4. Боты TG/MAX/VK: текст одинаковый, кнопки — штатные кнопки бота, пустая строка в ВК — только `<p><br></p>`. Подпись к картинке в TG ≤ 1024 знака. Делить на «(следом)» только по фразе в документе.
5. Сегмент — по разделу «Сборка сегмента» ниже. «Когда отправлять» — **всегда «При вызове из процесса или формы»** (`from_mission`) во всех каналах, дату не ставить. Картинка — как сказано в `config.md` (раздел «Режим»).
6. Сохранить, перезагрузить, сверить.

## Сборка сегмента

Сегмент — самое опасное место: ошибка = письмо уходит не тем людям. Поэтому:

1. **Сначала план словами.** Перевести ТЗ в дерево условий и показать пользователю вместе с таблицей разбора:
   `ученик` И (ИЛИ: зареган на вебинар 28.10; вход на вебинар 28.10) И НЕ (купил озвучку или подкаст).
   Связки читать буквально: «студент **и** был на вебинаре» = И, «зареган **или** был онлайн» = ИЛИ, «исключаем» = отдельный блок с «НЕ».
2. **Собирать из эталонов, а не с нуля.** Типовые блоки — в `../tsss-mailing-check/patterns.md`. Найти прошлую рассылку с таким же блоком (`tsssFind` из `../tsss-mailing-check/collect.js`), взять её `rule` (JSON) с ОТРИСОВАННОЙ страницы, заменить только то, что меняется: дату, вебинар, предложение, группу. id предложений и групп искать по точному названию с датой; не нашёл или нашлось несколько — спросить.
3. **Боты = условия email + ровно одно условие канала:** TG `user_telegram_connected`, MAX `user_max_connected`, VK `user_vk_connected`. Другой разницы быть не должно.
4. **Записать** `rule` в форму вместе с `ParamsObject[recipients_type]` = сегмент. При POST через fetch `rule` передавать обязательно — без него остаётся «Сегмент» без условий, то есть почти вся база.
5. **Проверить:** перезагрузить страницу, прочитать условия (`tsssReport`) и сравнить с планом из п. 1; посмотреть число получателей — неправдоподобное (0 или вся база) = стоп, сообщить.
6. Никогда не ставить «Всей базе» и не оставлять «Сегмент» с пустыми условиями.

**Запоминать сегменты (решение пользователя 26.10.2026):** перед сборкой сверить ТЗ с разделом «Готовые сегменты» в `../tsss-mailing-check/patterns.md` и копировать эталонный набор; после сборки и проверки нового или изменённого повторяющегося сегмента (предложения, группы, вебинары, id эталонных черновиков) САМОМУ дописать его в этот раздел, не дожидаясь просьбы. Проверяльщик (`tsss-mailing-check`) дописывает туда же то, что пользователь подтвердил как правило.

Перед отправкой сегмент независимо проверяет `tsss-mailing-check`.

## Правила от пользователя (26.10.2026)

- **ВЕСЬ текст — дословно из ТЗ/документа, ничего своего не писать** (решение пользователя 26.10.2026): ни слова не добавлять, не убирать, не заменять и не «исправлять» (опечатки автора — только списком в отчёт). Служебные пометки документа («Кнопка для е-мейл…», «Для картинки», комментарии) в текст не попадают. Допустимо только форматирование без изменения слов (абзацы, жирный, неразрывные пробелы); если сомнение, оставлять как в документе.
- **В начале КАЖДОГО бота (TG, MAX, VK) — две жирные строки: тема и прехедер из ТЗ** (решение пользователя 26.10.2026: «оставлять всегда»), затем пустая строка и текст.
- **Пометки ТЗ про каналы** («В бот только тему. Прехедер не надо», «Для е-мейл» и т.п.) выполнять буквально: в этом случае в боте одна жирная строка с темой. Если в ТЗ нет кнопок и ссылок — удалить блоки кнопок в почте и editor_buttons в ботах, ссылок не добавлять. Метки в тексте ТЗ («Кнопка или кликабельная ссылка:», «Кнопка:») в рассылку не попадают; подпись кнопки берётся из ТЗ дословно (даже с опечаткой).
- **Сегмент «только зарегистрированным»**: «ученик» И (заказ на предложение «… Регистрация на вебинар … [Авто]» ИЛИ группа с тем же названием) И НЕ(купил озвучку/подкаст); собирается из копии набора с широким исключением: оставить блок покупателей, остальные исключения убрать, добавить OR-блок регистрации.
- **Типограф GC — в ПОЧТЕ ставить** (уточнение пользователя 26.10.2026): после заполнения каждого текстового блока письма — «Типограф» (рецепт: `../gc-mailing/config.md`, п. 6; кнопка `.re-typograph`, события mousedown/mouseup/click при активном редакторе блока, затем пробел+BackSpace, клик мимо, «Сохранить»). Слова должны остаться теми же (сверить нормализованный текст до/после). В ботах типограф не запускать. Ловушка редактора: пока блок активен, панель Redactor перекрывает кнопку «Сохранить» — сначала кликнуть по серому фону справа от письма (панель исчезнет, кнопка «Сохранить» снова видна справа вверху), только потом нажимать её; размер окна меняется, координаты брать со скриншота. Сохранять и проверять перезагрузкой (nbsp, `<u>`, `<strong>`, слова). «Верстка как в ТЗ» = выделения (жирный, подчёркивание, курсив) и отступы (пустые строки); пробелы могут отличаться.
- **Форматирование как в ТЗ:** подчёркивание, жирный, курсив, пробелы (в т.ч. двойные и в конце строки) и пустые строки переносить один в один, как в документе; неразрывные пробелы самим не добавлять. Техника: разобрать HTML-экспорт в Chrome (в Google Docs нужен `trustedTypes.createPolicy` для DOMParser; стили лежат в классах `.cN` в `<style>`), собрать HTML абзац в абзац (пустой абзац документа = `<p><br></p>`, подчёркивание `<u>`, жирный `<strong>`, курсив `<em>`), после сохранения сверить абзацы с документом. Ограничения GC: в ботах конечные пробелы и nbsp в конце абзаца срезаются при сохранении, в почте последний пробел блока срезается; текст при этом совпадает. Брать форматирование из HTML-экспорта документа (`/export?format=html` в Chrome с входом в Google), а не из текстового.
- **Эмодзи, которые GC превращает в ⭐ при сохранении (🤩 U+1F929, 🤍 U+1F90D и подобные новые):** в ботах после сохранения проверить, нет ли ⭐, которой нет в документе; если есть — на открытой странице бота собрать `FormData(#yw0)`, заменить ⭐ на числовой код (`&#x1F929;`), POST на `form.action` с `save=1`, перечитать. В почте (конструктор) обхода нет — сообщить пользователю, что эмодзи нужно вставить вручную.
- **Тема и прехедер — строго из ТЗ/документа.** Дословно, ничего не добавлять (даже `{first_name}`, как было в прошлых письмах) и не брать из копии образца. Анонс для приложения у почты (`chatium_annotate`) = прехедер из ТЗ.
- **Тег «Событие | Новогодняя акция» в исключении «купил озвучку или подкаст» НЕ используем.** В копии прошлого набора он есть — удалить (оставить «Повышение тарифа» и «Покупка»): найти узел `deal_offer_id` с этим тегом в `rule`, убрать из `children`, записать `rule` в скрытое поле на открытой странице и нажать «Сохранить», затем проверить перезагрузкой.
- Картинку, скопированную с прошлого набора, можно оставлять, если ТЗ не говорит иначе; подпись в TG длиннее 1024 знаков допустима (Telegram отправит текст отдельным сообщением).
- **«Кнопка или кликабельная ссылка: <текст>» в ТЗ (правило пользователя 30.10.2026):** в БОТАХ (TG, MAX, VK) это не кнопка, а фраза в тексте на том месте, где стоит пометка, с вшитой ссылкой своего канала (`<a href>`, UTM канала); отдельную кнопку бота для неё НЕ делать (editor_buttons только для пометок «Кнопка:»). В ВК ссылка для «Кнопка:» — в конце текста. В ПОЧТЕ обе пометки — кнопки конструктора. Пример: набор «Распродажа 02.11.26» — «Хочу на распродажу» ссылкой в тексте, кнопка бота только «Пройти регистрацию».

## Шаг 3. Самопроверка и передача на проверку

- Перечитать каждый черновик: тема, прехедер, текст по SHA-256 против документа, порядок абзацев, подписи и ссылки кнопок, `<vk-snippet-end/>`.
- Почта: «Типограф» и «Анализ текста» GC (рецепт — `../gc-mailing/config.md`, п. 6 и 8).
- Предложить пользователю запустить проверку скиллом `tsss-mailing-check` в режиме «проверь вёрстку» — проверяющий смотрит независимо.

## Отчёт

По каждому письму: ссылки на черновики «EMAIL / TG / MAX / VK», что поставлено и что осталось пользователю (сегмент, время, картинка — по `config.md`), расхождения UTM, опечатки, указания из комментариев.
Напомнить: тестовое письмо себе и отправку делает человек.
