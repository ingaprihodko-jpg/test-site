# Проверка рассылок tsss.site

Вход от пользователя: **ТЗ** (когда, кому, кого исключить, каналы, картинка) + **ссылка на рассылку** (обычно одна, чаще [EMAIL]) + **ссылка на Google Docs** с текстом.
Выход: отчёт «ошибки / уточнить / в порядке» по каждой рассылке набора.

Перед началом прочитай `patterns.md` — там эталоны сегментов, UTM и названий tsss.

## Жёсткие запреты

- Только чтение. НЕ нажимать «Сохранить», «Готово к отправке», «Отправить», «Тестовое письмо», не менять поля, не удалять.
- Не открывать список сообщений получателей и профили пользователей.
- Не исправлять самому, даже очевидное. Ошибки — в отчёт.
- Пароли не вводить: пользователь залогинен в Chrome.

## Инструменты

- GetCourse — Claude in Chrome (`mcp__claude-in-chrome__*`). Загрузить сразу пачкой: tabs_context_mcp, tabs_create_mcp, navigate, javascript_tool, computer.
- Google Docs — `read_file_content` (Drive-коннектор). Он ОБРЕЗАЕТ длинные документы (~5 тыс. знаков). Если текст оборван — открыть в Chrome `https://docs.google.com/document/d/<ID>/export?format=txt` и прочитать `get_page_text`.

## Шаг 1. Разобрать ТЗ

Выписать в таблицу: дата и время (перевести «завтра/сегодня» в дату — если дата ТЗ неясна, сверять с названием рассылки и спросить при расхождении), каналы, «отправляем тем, кто…» (ИЛИ-список), «исключаем…» (каждый пункт отдельно), картинка.
Обращать внимание на связки: «студент **и** был на вебинаре» = И, «зареган **или** был онлайн» = ИЛИ.

## Шаг 2. Собрать рассылки

1. Открыть ссылку пользователя в новой вкладке (без `?scan=…`).
2. Вставить содержимое `collect.js` через `javascript_tool` (одним вызовом, как есть).
3. Найти весь набор: `await tsssFind('<общая часть названия>')`, например `БАЛЛЫ [24.10.26` или `дожим веба 23.10.26`. Должно быть 4 канала: EMAIL, TG, MAX, VK (если ТЗ не говорит иначе).
4. `tsssCollect([ids])` → затем `await tsssWait()` (повторять, пока «готово»). Не ждать сбор в одном вызове — таймаут 45 с.
5. `tsssReport(id)` по каждой; для email ещё `tsssReport(id, true)` (с текстом). Для ботов — `tsssSegDiff(emailId, botId)`.

Ограничения вывода `javascript_tool`: длинная строка обрезается (~1000 знаков) — функции уже возвращают массив коротких строк; строки с `?`, `&`, `=` блокируются — функции их заменяют.
Во время сбора НЕ переходить на другие страницы в этой вкладке — данные пропадут.

## Шаг 3. Проверить

**Набор и время**
- Есть все каналы из ТЗ; в названиях `[EMAIL]/[TG]/[MAX]/[VK]`.
- `need_send_at` совпадает с ТЗ и со временем/датой в названии; у всех каналов одинаковое.
- Статус: черновик / «Готовится к отправке» — норм; «Завершена» — только сообщить.

**Сегмент** (главное)
- Каждый пункт ТЗ найден в условиях, и наоборот — нет лишних условий.
- И/ИЛИ и галочки «НЕ» совпадают со смыслом ТЗ (частая ошибка: условия, которые должны быть через И, стоят отдельными ветками ИЛИ).
- Вебинары, предложения, группы — по названию и ДАТЕ (не прошлый вебинар).
- Даты: «по 22 октября включительно» → `to: 22.10.2026`; «с 1 сентября» → `from: 01.09.2026`.
- Типовые блоки сверить с эталонами из `patterns.md`.
- Тип пользователя «ученик» есть.
- Бот = email + ровно одно условие подключения канала. Любая другая разница — ошибка.

**Ссылки и UTM**
- Ссылка/кнопка та, что в документе (тот же адрес).
- UTM как в документе для ЭТОГО канала. Если в документе ссылка без метки — без метки норм (не ошибка).
- Типичная ошибка: в TG/MAX/VK осталась ссылка с `medium=email` (скопировали из email).
- У TG/MAX кнопки в превью не видны, если рассылка не черновик — писать «кнопку проверить не могу», не «ошибка».

**Картинка**
- Email: в шаблоне картинка соответствует ТЗ («Логотип школы» = файл `Лого TSSS.jpg`, sc/397; «с приветственного» — та же, что в письме регистрации, sc/233). Боты: приложенный файл (`файлы:`).

**Текст**
- Email: в «HEAD письма» есть `<vk-snippet-end/>` — ОБЯЗАТЕЛЬНО (правило пользователя 26.10.2026); нет — ошибка.
- ВЕСЬ текст дословно из документа: любое добавленное, пропущенное или изменённое слово — ошибка (неразрывные пробелы и разбивка на абзацы — не ошибка).
- Тема и прехедер — строго как в ТЗ/документе, ничего лишнего (в т.ч. `{first_name}`, которого в ТЗ нет). Тег «Новогодняя акция» в исключении «купил озвучку» — ошибка.
- Тема/прехедер/текст — как в документе, абзацы в том же порядке, ничего не потеряно. `{first_name}` написан правильно.
- Опечатки и расхождения — списком с цитатой, без правок. Латинские буквы в словах вроде «бeсплaтный», «бoнусные» — это намеренно (антиспам), не ошибка.

## Режим «проверь вёрстку» (после агента tsss-mailing)

Включается, когда просят «проверь вёрстку» или черновики собрал `tsss-mailing`. Делается ВСЁ из шага 3 (сегмент тоже — его собирал агент) плюс:

- **Набор:** все 4 канала, названия по эталону, у всех один хвост `[дд.мм.гг] в ЧЧ`.
- **Когда отправлять:** у черновиков агента везде «При вызове из процесса или формы» (`from_mission`), без даты — это правильно, не ошибка; другое значение — ошибка. Время сверять с названием.
- **Почта:** тема и прехедер слово в слово; в «HEAD письма» есть `<vk-snippet-end/>`; абзацы не слиплись и нет лишних пустых; жирный и списки как в документе; число, порядок и подписи кнопок как в документе, у каждой кнопки есть ссылка (пустой `href` — ошибка); эмодзи не превратились в ⭐ (🤍 GC ломает); `{first_name}` цел.
- **Боты:** текст TG = MAX = VK; подпись к картинке в TG ≤ 1024 знака; в VK нет слипшихся абзацев; кнопки — штатные, с ссылками этого канала (`medium=tgbot / max / vk`); «(следом)» только там, где в документе фраза «следующим сообщением».
- **Не трогать:** латинские буквы в словах — намеренный антиспам.

В отчёте разделять: «ошибки вёрстки» и «ошибки сегмента».

## Шаг 4. Отчёт

Коротко, по-русски:
1. **Ошибки** — что, где (канал + ссылка на рассылку), как в ТЗ / как в GC.
2. **Уточнить** — спорное (например, разные теги, которые могут быть одинаковыми).
3. **В порядке** — одной-двумя строками.
4. **Не проверено** — что не удалось (кнопки ботов, обрезанный документ).

Повторяющиеся сегменты (когда ТЗ совпадает с уже собранным ранее) сверять с разделом «Готовые сегменты» в `patterns.md`; новый подтверждённый сегмент дописывать туда же.
Новые подтверждённые пользователем правила (например, «эти теги одинаковые») дописывать в `patterns.md`.
